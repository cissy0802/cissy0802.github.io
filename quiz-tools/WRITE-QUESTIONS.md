# 出题指南

题目给 hub 的所有登录读者做，他们读过或没读过这篇。目的是**检验读者真的带走了文章最值钱的东西**，不是考记忆力。

## 输入

`work/batch.json` 的每篇文章有 `src`（正文纯文本，`text_truncated` 为 true 时后面还有内容）。每篇都要读完 `src` 再出题。

## 出多少

每篇最多 3 题。质量决定数量：撑不起 3 道好题的短文就少出，一题都撑不起就不出。

## 什么样的题算好题

判断标准只有一个：**真读懂这篇的人能答对，只扫过标题或凭常识的人会答错。**

- 考核心论点、关键机制、反直觉的结论、作者的具体区分，而不是年份、人名、数字这类细枝末节——除非那个数字本身就是要点。
- 同一篇的几道题考不同的点。
- 好的题常常是「应用」或「辨析」：给一个情境问文章的框架会怎么判断；或者把文章的观点和一个听起来很像、但文章明确反驳的说法放在一起。
- 干扰项要**似是而非**：常识里的误解、文章提到又否定的观点、因果搞反、两个概念混淆。不放一眼就能排除的凑数选项。
- 题干要自足，脱离文章上下文也知道在问什么，不要写「这篇文章」之外无法理解的指代。
- 门槛是「凭标题或常识答不出」，常识按这篇的目标读者算。技术文章本来就讲行业知识，这没问题，考文章自己的判断和取舍；非技术文章里的技术类比是助读，不是考点。
- 文章当作定论、但学界有争议或复现失败的研究结果，不要拿来出题。发现这种情况就在汇报里点名，方便回头改稿。
- 解释里不要用「第二项」「前者」这种位置指代，选项会被打乱，要直接说内容。
- 用中文，简洁。选项长度大致相当，正确答案不要总是最长的那个，`build` 会按整批检查。留意「最严谨、带限定条件的那个就是答案」这种可学的套路：让一两个干扰项也同样讲究分寸。
- `text_truncated` 为 true 时只考看得到的正文。
- 不假设读者的年龄、性别、职业。

## 辩论（thinker-arena）

辩论页的 `src` 以「辩论：」开头，结构是先【结论：三份总结】，再【辩论过程】。读者该带走的是**辩论最后落在哪里**：共识是什么、它为什么站得住、能拿去怎么用。

- 题目从结论出发。辩论过程只用来理解结论是怎么得出的，不单独出题。
- 不考谁说了什么、谁反驳了谁、各方的分歧在哪。题干和选项里不出现参与者的名字，`build` 会拦。
- 支撑共识的某个机制或例子可以考，但要把它当作观点本身来问，不挂在某个人名下。
- 好的辩论题常常是给一个情境，问按这场辩论的共识该怎么判断；干扰项可以用辩论中被否定的立场来写。

## 输出

写 `work/draft.json`，然后运行 `python3 bank.py build`，按提示改到 OK：

```json
{"questions": [
  {"slot": 1,
   "question": "题干",
   "options": ["正确答案", "干扰项", "干扰项", "干扰项"],
   "explanation": "两三句：为什么对，以及最诱人的那个错项错在哪。",
   "question_en": "The same question in English",
   "options_en": ["Correct answer", "Distractor", "Distractor", "Distractor"],
   "explanation_en": "The same explanation in English"}
]}
```

**正确答案永远写在 options 第一个**，脚本会打乱顺序。`options_en` 必须和 `options` 一一对应、顺序相同。

英文要写得像英文母语者出的题，不要逐字翻译；术语用英文学界和原书的通行说法。
